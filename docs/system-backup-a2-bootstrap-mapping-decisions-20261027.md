# A2：bootstrap typed mapping 决定核对

本轮核对现有 **20 个 bootstrap reference、23 种 SecretRef purpose、15 种已实现 metadata 对应**。其中 5 个 bootstrap 用途没有单一 SecretRef 对应；Schema 另外 8 种 purpose 也不能自动变成新槽位或别名。CLI 当前缺项仍为 27，本审计清槽 0。

具体枚举、原来源/准确摘要及每项所需原始事实见[机器清单](evidence/a2-bootstrap-mapping-decisions-20261027.json)。这是缺失决定核对，不是新授权或合同批准。

| 决定 | 范围 / 协调 owner | 已有实现或原合同事实 | 还缺的明确决定 | 可继续的本地动作 |
| --- | --- | --- | --- | --- |
| M1 | 全部 15 种 metadata 对应与其余资源；A/D；资源原 owner | DecodeSecurityReference 校验完整字节/闭集；MatchesBootstrapPin 仅比 purpose/identity/version；CaptureCandidateRelation 明确是关系 DATA，原 authority 必须独立认证部署、用途、provider/scope、候选及当前状态。 | 必须指出现有哪一条独立受控来源认证完整 ref→provider/scope/purpose→C1 admission/target/profile 关系，以及当前撤销/期限如何复核。摘要、构造成功和 receipt 不得自证这一来源。 | 给原 authority 的已有接口逐方法标出实际来源和未实现接点；可复用固定 grant/RBAC/文件及关系检查，不增加新 grant/approved DTO。 |

| M4 | evidence_store；A；D evidence channel | S3Config 已有 installation、Identity、Version、endpoint/bucket/root/CA；store identity 不是某一个 credential，SecretRef 没有 store-kind。运行组件仍消费已准入映射。 | 指出原 typed store/root 的来源，并把对象不可变版本/完整性/保留、故障域和权限隔离与原 evidence channel profile 完整关联；不能从连接成功或 store hash 推导授权。 | 对照现有 S3Config/Ref/channel 字段列出 mandatory resolver 输入和拒绝条件，复用已有读写/缺失协议。 |
| M5 | status_relay；B 服务；D 当前 Job cursor；A 工作身份 | SecretRef 无 status_relay purpose/kind；Job cursor 已有 job_uid/generation、relay_identity_ref/version/bound_at/expires_at、sequence/body hash。六类 capability role 中没有可自动替代 relay 的新角色。 | 明确真实 relay 服务/客户端 mTLS 身份与原 Job UID/generation/task/attempt、绑定期限/序列/撤销的权威关联；不能以 relay 自报或普通 Secret 名称代替。 | 把 runner/Job cursor 的现有字段对照到 B 原服务合同，保留重放、错 attempt 和撤销拒绝；不扩 provider enum 或硬塞 SecretRef alias。 |
| M6 | catalog_snapshot → catalog_discovery；C；A 来源复审 | 已有 draft metadata 对应，credential_capability 可为 snapshot_list 或 inventory_read；evidence S3 Store 的 Stat/Range/Put/Delete/Absent 不提供 catalog discovery 完整性。 | 在原 ref/version/provider profile 下明确选择哪一种发现模式、精确 manifest/version/checksum、覆盖和缺失证明规则；不能从 supported 列表自动挑模式或在失败时换模式。 | 按两种原模式列出所需输入及拒绝分支，接 C 原 discovery adapter；不混用 inventory 与 snapshot 结果。 |
| M7 | catalog transport 的 CA 来源；C 传输；A 信任复审 | Schema CA purpose 有 catalog_ca，但 bootstrap 20 refs 没有 catalog_ca；现有具体 CA validator 只接受 artifact_ca/evidence_ca。这不是自动增加第 21 个槽位的授权。 | 明确 catalog adapter 在现有合同下从哪里取得并验证原 CA bundle、hostname/允许目标及其 provider/scope/版本绑定；不得擅自将 catalog_ca 折成 artifact_ca。 | 核对 C 原 catalog 连接 profile 的 trust 字段和 A 可复用的校验接点；需要合同决定时写明原来源。 |
| M8 | capture / acceptance / catalog signing；A signer；B capture/C catalog payload，D 组合 | 三 purpose 映射、EdDSA/domain、三用途 key history/retention 和 capture 关系已实现。SecretRef identity_version 可为非数字 token；TransitSigner 的 Vault version 必须是规范正整数。Capability 正文不是签名授权或实际 challenge 认证。 | 由原来源明确 ref identity/version→provider key ID/numeric version/public key、purpose/domain/payload、调用身份/权限，以及实际探针输入/验证与原 C1 run/profile 的关系；不能剥 version 前缀、使用 latest 或仅凭 healthy 认证。 | 复用 signer、原历史隔离和关系比较，准备准确 typed 关联及独立原 authority 接点；未有原探针合同就不自造签名授权/challenge grant。 |
| M9 | nonce_hmac 的 profile 与全局版本归属；A | 具体 validator 支持受控 exact-version external_secret 文件，真实 32 字节/wipe/原期限；candidate 锁全局配置及固定 cutoff retained 行。版本映射按原 ledger 的 version 定位，冲突 identity 会拒绝。 | 原部署必须明确采用已支持的文件 profile，并给出所有受保留版本的唯一/一致 identity 归属与保护期；Kubernetes Secret UID/API profile 不能由文件或哈希外观冒充。 | 保留已实现的全局歧义/撤销/期限拒绝并显式组合；若原部署使用其他 profile，需要它的真实 owner adapter。 |
| M10 | evidence_read_write 与三个精确 evidence credential 槽；A | 该 Schema purpose 只允许 exact_write/exact_read/conditional_create/range_read，不包含 delete/append/discovery；也不在 15 个 bootstrap metadata 对应中。Go 多收四项的偏差已精确修复；Schema 驱动反例/正例、完整五包、准确材料 seed、Linux 编译及来源后检/清理均有受限组合接收，已落地准确两源码。 | parser 现已符合既有四能力限制；仍须沿原 evidence_write/read/delete 分离策略给出真实权限，不得以 combined descriptor 填三槽或从 metadata decoder 推导授权。 | 保持已验证的准确窄修，不再重复同范围 Go；接入时仍核对三精确凭据原身份和分离权限，当前全树基线由另一个准确窗口验证。 |

provider capability 表中的 `evidence_read_write` 多收四项的本地偏差已关闭；[窄修候选](evidence/a2-reference-capability-parity-candidate-20261026.json)没有改 Schema、原 vectors、15 个 metadata 对应或授权。其余 9 个 provider-purpose 的能力集合与 Schema 相同。准确旧反例/修复回归及五包、当前材料 seed/Linux 六项均已完成来源后检/清理，组合接收和精确落地证据见机器清单；旧 9c2f 整轮失败保留。

M2–M8 列出的原 owner 决定须提供现有受控来源或准确合同决定；不会用新 grant、approved DTO、provider enum 或 alias 替代。M9 已有受限 profile 的实现，须核对原实际部署事实；M10 的本地 parser 修复已闭合，但三精确凭据的原授权事实仍须认证。所有 Schema draft 状态、未核实现场状态和未验边界均保留。
