原共享 `RecoveryAuditJournal.append` 在进入方法时检查 context，随后用普通互斥锁等待。若 context 在这两个动作之间或排队期间取消，请求仍会等待前一写入结束。下载/GC 的失败标记又要取得同一把锁，取消的故障报告可能再次卡在标记失败这一步。

新实现使用可取消的 writer 队列；取得写权限后再次检查取消与失败状态，并保留完整 Write/Sync 的串行所有权。失败标记改为原子锁存，不等待 writer；Close 先阻止新写入，再等待已有写入退出并关闭文件。未触碰 IO 的普通恢复审计排队取消不会损坏健康日志，下载/GC 故障 wrapper 则保留原来的永久失败语义。

验证包含两个只存在于自有临时目录的 Go overlay：分别恢复不可取消的锁等待和阻塞的失败标记。旧语义准确触发两个取消/超时叶子及四个下载/GC 叶子失败，健康并发完整记录对照仍通过。去掉 overlay 后，定向 23 根/162 项通过，原始错误注入失败按预期保留，不记成通过。该冻结的首次取消检查由确定性 context 握手控制；最终完整包另强化了已进入等待后的取消观察。

文件身份、容量、权限、单写者、换行、fsync、原始授权/期限与记录格式不变。context 只中断排队及各 IO 前后的边界，不能强行中断已经进入内核的普通文件 Write/Sync；没有启动后台写入来伪造超时后的持久化结果。现场持久卷、实际 SQL/provider、完整 GC policy 与启用仍需原验收。
